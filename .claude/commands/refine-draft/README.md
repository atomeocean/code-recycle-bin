# /refine-draft 使用说明

把一份写得比较随意的需求草稿 / 笔记，先**只改语句、不改内容**地润色一遍，再压缩成一份可以直接发给团队评审的简报。
一次运行同时给出两份产出。

命令文件：[refine-draft.md](../refine-draft.md)

## 这个命令会做什么

**第一步：润色草稿（内容不变）**

1. **改语句**——语法、标点、语序、长句拆分，把绕口或重复的表达改成直白说法。
2. **统一术语**——草稿里同一个东西有多种叫法时，取出现最多的那个，全篇统一。
3. **补清指代**——「它 / 这个 / 那边」在草稿里本来就指得明白时，替换成具体对象。
4. **原样输出结构**——顺序、段落、条目数量都不变，以代码块形式贴出，方便复制。

**第二步：压成评审简报**

5. **压缩**——在润色稿的基础上，压成 `需求` / `背景` / `待确认` 三段，一眼能读完。
6. **保细节**——具体约束（谁提的、哪个页面/系统、数字、时间节点）一个都不丢。
7. **只标不猜**——真正含义不明的地方不臆测，最多在 `待确认` 里列 2–3 条。

不会做的事：不加验收标准、不加方案建议、不估工时、不删细节、不写文件。简报是**评审前**的东西，
不是开发用的规格。

## 输出长什么样

````
```
<润色后的完整草稿，长度与原文相当>
```

---

**需求**：……

**背景**：……

**待确认**：
- ……
````

润色稿在代码块**里面**（方便直接复制），简报在**外面**。

## 怎么用

显式调用 `/refine-draft`，把草稿文本作为参数传入。例如：

```
/refine-draft 支付页那边现在有点乱，用户说结算页的按钮找不到，7月底之前想优化一下，负责人是小王
```

不带参数直接运行 `/refine-draft` 时，会先反问要润色的草稿。

传 GitHub issue 链接或文件路径时，会让你直接粘贴原文，不会去抓取或打开文件。

> 注意：这是一个显式命令，不像技能（Skill）那样根据对话内容自动触发，需要手动输入 `/refine-draft`。

## 什么时候用哪个

| 需要的效果 | 用这个 |
|---|---|
| 把话说顺说清楚，并压成评审用简报 | `/refine-draft` |
| 扩写成完整的 Feature Request issue（含验收标准） | `/issue:new-to-backlog` |
| 估算开发工时 | `estimate-issue-hours` 技能 |

典型顺序：先 `/refine-draft` 把草稿说清楚、拿简报给团队评审 → 评审通过后用 `/issue:new-to-backlog`
落成 issue → 需要排期时用 `estimate-issue-hours` 估工时。

完整规则见 [refine-draft.md](../refine-draft.md)。
